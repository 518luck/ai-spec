# Claude Code 配置体系：AGENTS.md / Skills / Agents / Plugins 的真实关系

> 严重：Info（认知澄清，非运行时 bug）
> 类别：产品领域认知 / 信息架构
> 来源：[Claude Code 官方文档 - Plugins reference](https://code.claude.com/docs/en/plugins-reference)、[plugin-dev 工具链](https://zread.ai/anthropics/claude-code/21-plugin-development-toolkit)

## 问题

项目侧边栏「AI 规约」分组曾把 **AGENTS.md / Skills / Agents / Plugins** 列为平级菜单项。需要厘清四者的真实概念关系，判断这个平级结构是否合理——否则信息架构会层级错乱。

## 根因：四者的真实关系

从官方文档确认，**Plugin 是顶层容器（可分发的打包产物），Skills/Agents/Hooks/MCP 是它的组成部分**；但 Skills/Agents 同时也是**独立的创作单元**，用户分别编写、迭代它们，最后才组合打包成 Plugin。AGENTS.md 则是完全独立维度的项目文档。

```
Plugin（自包含目录，可分发——是"打包结果"）
  ├ skills/      ← 用户可调用的 /name 技能（独立创作单元）
  ├ agents/      ← 专用子代理（独立创作单元）
  ├ hooks/       ← 事件处理器
  ├ .mcp.json    ← MCP 服务器
  └ .lsp.json    ← LSP 服务器
```

| 概念 | 本质 | 作用域 | 与其他的关系 |
| --- | --- | --- | --- |
| **AGENTS.md** | 项目文档（markdown） | 绑定到具体代码仓库 | 独立维度，和 Plugin 体系无关 |
| **Skills** | 独立创作单元（高频编辑） | 个人全局或项目级 | 既是独立资源，也是 Plugin 的组成部分 |
| **Agents** | 独立创作单元（高频编辑） | 个人全局或项目级 | 既是独立资源，也是 Plugin 的组成部分 |
| **Plugin** | 打包产物（低频组合发布） | 可个人安装，也可项目级安装 | 顶层容器，把 Skills/Agents/Hooks 组合分发 |

### 关键认知：创作单元 vs 打包产物

- **创作单元**：Skill / Agent / Hook——用户日常高频编写、测试、迭代的对象
- **打包产物**：Plugin——把已写好的散件组合进一个目录加 manifest，低频的"发布"动作

官方 `plugin-dev` 工具链的 `/plugin-dev:create-plugin` 是 **8 阶段工作流**，先分别开发 skill-dev / agent-dev / command-dev，最后才组合成 Plugin。Skills 和 Agents 各有独立的开发章节，证明它们是独立创作对象。

**因此 Skills/Agents 不该埋进 Plugin 详情里**——那会让用户为编辑一个 Skill 要先找包裹它的 Plugin，本末倒置。

### AGENTS.md 的额外约束

- 单个 AGENTS.md 文件**不应超过 200 行**
- 因此一个真实项目通常**拆成多份 AGENTS.md**，散落在不同子目录（如 `AGENTS.md`、`app/api/AGENTS.md`、`src/AGENTS.md`）
- "项目内有多份 AGENTS.md"是真实高频需求，不是伪层级

## 结论：导航层级应为

### 核心依赖链

```
规约(Rule)        ← 原子化的单条约定，用户收集拼凑
   ↓ 拼凑组合进
AGENTS.md         ← 项目级文档，200 行限制 → 单项目多份
   ↓ 绑定到
项目(Project)     ← 真实代码仓库
```

### 决策：以「项目」为中枢

用户主操作路径：

```
侧边栏: 项目(一级)
  └ 进项目 → 看这个项目的 AGENTS.md → 编辑某份 → 从规约库挑规约拼进去
```

用户心智：「我在管 ai-spec 这个项目，它的 AGENTS.md 需要补充，我去规约库找几条拼进来。」

理由：AGENTS.md 一般绑定到项目、很少通用；规约的终态归宿是拼进 AGENTS.md。因此用户的终态目标总是「某个项目的 AGENTS.md」，项目是天然的入口枢纽，规约库作为素材库从项目内调用。

### 侧边栏「AI 规约」分组结构

四项平级，各有独立管理界面：

| 入口 | 管理对象 | 性质 |
| --- | --- | --- |
| **项目** | 真实代码仓库 → 项目内多份 AGENTS.md | 容器，组装中枢 |
| **规约库** | 原子化规约（全局独立素材） | 独立资源，通过「拼进 AGENTS.md」动作连接项目 |
| **Skills** | 独立创作单元（高频编辑） | 独立资源，可个人全局或项目级 |
| **Agents** | 独立创作单元（高频编辑） | 独立资源，可个人全局或项目级 |
| **Plugins** | 打包分发的扩展包 | 低频组合发布产物 |

### 个人空间侧边栏目录分配

两个分组：项目拎到分组 1 与规约库并列（组装中枢地位凸显），Skills/Agents/Plugins 独立成「资源」分组：

```
个人空间

├─ 内容             ← 分组 1（无标题）
│   ├ Prompt
│   │   ├ 收录
│   │   └ 草稿
│   ├ 规约库         ← 原子素材库
│   └ 项目          ← 组装中枢，和规约库并列
│       └ AGENTS.md（项目内文档，不独立成菜单项）
│
└─ 资源             ← 原"AI 配置"改名
    ├ Skills
    ├ Agents
    └ Plugins
```

- 项目拎到分组 1：凸显组装中枢地位，和规约库对等（规约是素材，项目是组装成品归属）
- AGENTS.md 收进项目内：点项目 → 看项目内多份 AGENTS.md
- 资源分组：Skills/Agents/Plugins 都是用户创作/拥有的资源，"资源"比"配置"准确

### 规约 → AGENTS.md 的引用机制

**决策：版本化引用（固定版本 + 可选升级）**

规约拼进 AGENTS.md 时，采用「引用 + 固定版本」模式，而非纯引用或纯复制：

```
规约 v1 ──引用(固定 v1)──→ AGENTS.md A（项目 X）
规约 v1 ──引用(固定 v1)──→ AGENTS.md B（项目 Y）
规约 v2（更新后）──可选升级──→ AGENTS.md B 主动升到 v2
```

| 需求 | 矛盾点 | 版本化如何化解 |
| --- | --- | --- |
| 规约要可复用 | 同一条规约用在多处 | 引用关系复用，不复制内容 |
| 已用规约要稳定 | 规约更新不该污染已引用处 | 固定版本，更新不自动传播 |
| 规约要能迭代 | 修了 bug 要能推广 | 可选升级，用户主动拉新版本 |

> 本质是依赖管理的经典模式（如 npm 锁版本 + 可升级），规约就是「文档的依赖项」。基础设施已有 `RuleVersion` 模型支撑。

**为什么不选纯引用/纯复制**：
- 纯引用：规约改了所有引用处自动变，Next 项目可能被未经验证的新版本污染
- 纯复制：规约改了已拼进去的不变，失去「原子复用」价值，退化成剪贴板

### 组装入口：双向

| 入口 | 服务的心智 | 说明 |
| --- | --- | --- |
| AGENTS.md 编辑器内「插入规约」 | 「我在写这份 AGENTS.md，需要补充内容」 | 编辑时从规约库挑规约插入 |
| 规约详情页「应用到 AGENTS.md」 | 「我攒了条好规约，想塞进项目」 | 选目标项目 + 文档推送 |

两个入口服务两种出发心智，互为补充，最终都指向同一个底层操作（建立版本化引用关系）。

### 升级提示：双向

规约从 v1 升到 v2，已引用 v1 的 AGENTS.md 怎么知道有新版本？

| 提示位置 | 服务的场景 | 说明 |
| --- | --- | --- |
| AGENTS.md 编辑器内标「v1→v2 可升级」 | 「我在编辑这份 AGENTS.md，顺手升级」 | 引用的规约旁显示可升级，点击才升，低打扰 |
| 规约详情页「被 N 份引用，其中 M 份可升级」 | 「我改了这条规约，想推广到所有用到的地方」 | 从规约视角推动升级 |

## 要点

1. **区分创作单元和打包产物**：Skill/Agent 是高频创作对象，Plugin 是低频组合结果。别因为"Plugin 包含 Skills"就把 Skills 降级——用户编辑的是 Skill，不是 Plugin。
2. **AGENTS.md 是项目级文档，独立维度**：和 Plugin 体系正交，作用域不同（项目仓库 vs 个人/项目可装）。
3. **AGENTS.md 中间层必须保留**：它是「规约集合 → 真实仓库文件」的物化形态。规约是原子素材，AGENTS.md 是组装成品，项目是成品归属。去掉它规约就退化成散乱标签，无法落地成 `.md` 文件。
4. **200 行限制驱动"项目内多文档"需求**：单项目必然有多份 AGENTS.md，"项目"是有价值的组织层。
5. **侧边栏反映用户操作对象，不反映技术包含关系**：菜单按"用户日常编辑什么"组织，不按"代码里谁包含谁"组织。
6. **规约引用用版本化模式**：固定版本 + 可选升级，兼顾复用、稳定、迭代三个矛盾需求。
7. 这份认知是「AI 规约」分组信息架构设计的**前置约束**，改导航前必读。
