## 一、高危问题（P0，建议立即处理，16 项）

### A. 鉴权与安全（4 项）

**1. 全站页面路由没有任何服务端鉴权守卫** — `proxy.ts:9`
Next 中间件入口 `proxy.ts` 是空实现（仅 `NextResponse.next()` + TODO），`app/spec/(dashboard)/layout.tsx` 也不校验 session，整个 `app/spec` 树只有 `team/layout.tsx` 调了 `await auth()`。未登录用户可以完整浏览 `/spec/personal/**`、`/spec/settings/**` 的页面外壳（profile 页甚至用 `|| ""` 渲染出空姓名/邮箱），数据请求 401 后还会触发全局 SWR onError 弹错。
**修法**：在 `proxy.ts` 对 `/spec` 下除 `(auth)` 组外的路径做 session 检查并 redirect（NextAuth v5 可用 `auth` 包装）；或至少把 `team/layout.tsx` 的守卫模式上提到 `app/spec/(dashboard)/layout.tsx` 统一拦截。

**2. debug 端点完全无鉴权，可被外部滥用发邮件/刷日志** — `app/api/debug/email/route.ts:6`、`app/api/debug/axiom/route.ts`
两个 debug 路由都是裸 `GET` 导出，无 withSession、无 NODE_ENV 门控。任何人访问 `/api/debug/email?to=任意邮箱` 就能用项目的 Resend 账号真实发出 3 封邮件（默认收件人还硬编码了私人 QQ 邮箱），可被用作垃圾邮件中继，消耗配额并损害发信域名信誉。
**修法**：至少包 `withSession`；更稳妥是生产环境直接 404（`NODE_ENV` 或专用开关），并移除硬编码邮箱。

**3. rules / rules/[id] / folders / tags 全部漏配 permissions，API Key scope 被整体绕过** — `app/api/rules/route.ts:25` 等
`withPersonal` 只在路由声明了 `permissions` 时才校验 API Key scope。prompt 系列和 `/api/rules/spaces` 都正确声明了，但核心的 `/api/rules`（GET/POST）、`/api/rules/[id]`（GET/PUT/DELETE）、`/api/folders`、`/api/tags` 全部没传第二参——一把零 scope 的 Key 也能完整读写规约、文件夹、标签，已登记的 `rules.read`/`rules.write` 形同虚设。（注：ownerId 数据隔离仍生效，不构成跨用户越权，但 scope 收紧机制失效。）
**修法**：逐路由补 `{ permissions: ["rules.read"] }` / `["rules.write"]`；folders 可按 `type` 参数映射对应资源的权限点。长远看建议把 `withPersonal` 的 `permissions` 改成必传（见"结构梳理"第 5 条）。

**4. Prisma / 未知错误的原始 message 直接回传给客户端** — `src/server/errors/http-error.ts:79`
`toError` 的 Prisma 分支和兜底分支都把 `e.message` 原样返回（Prisma 错误常含表名、列名、约束名），攻击者可借构造异常输入探测数据库结构。同项目的 `safe-action.ts` 对 Server Action 是脱敏的，HTTP API 却不脱敏，策略自相矛盾。
**修法**：对齐 safe-action——除 P2025 映射为通用"资源不存在"外，DATABASE_ERROR/INTERNAL_ERROR 一律返回固定文案，原文只进 Axiom 日志。

### B. 权限与后端正确性（3 项）

**5. 通配 scope（apis.all / apis.read）未被识别，"全部权限"的 Key 反而全部被拒** — `src/server/middleware/with-personal.ts:52`
权限校验只做精确匹配 `scopes.includes(p)`，而前端创建 Key 的"全部/只读"预设存的是 `["apis.all"]`/`["apis.read"]` 字面量。持全权 Key 访问任何声明了 permissions 的路由（如 prompt 系列）都会 403。
**修法**：校验前展开通配 scope（`apis.all` 直接放行、`apis.read` 放行所有 `*.read`），并补一条"apis.all 能通过 promptRecord.read"的单测。

**6. 个人默认领域空间 find-then-create 并发竞态，会创建多个默认空间** — `src/server/utils/rule-space.ts:14`
规约页首屏会同时并发三个都调用 `getOrCreatePersonalRuleSpace` 的请求（spaces、folders、rules），新用户首次进入时三个请求都查不到空间、都执行 create；`RuleSpace` 又没有 `(ownerId, teamId, name)` 唯一约束兜底，之后规约/文件夹会分散落在不同"默认"空间里。POST spaces 的同名查重同理。
**修法**：schema 加 `@@unique`（或 isDefault 标记列 + 唯一约束），函数改 upsert 或 create + P2002 捕获后重查，保证并发幂等。

**7. AXIOM_TOKEN 缺失时 import 即抛错，日志降级分支永远不可达** — `src/server/infrastructure/axiom/axiom.ts:6`
模块顶层 `new Axiom({ token: getEnv("AXIOM_TOKEN") })`，token 为空直接抛；`server.ts` 无条件 import，所以 `.env.example` 默认配置下后端启动即崩溃，"缺 token 降级 ConsoleTransport"的设计无法实现。
**修法**：axiomClient 惰性初始化（仅 `isAxiomEnabled` 为真时构造），或允许返回 null 由 server.ts 决定 transport。

### C. 规约库双视图改造的接线缺口（3 项）

**8. 搜索的 filter 维度是假 UI，且切换后开发环境直接崩溃** — `src/pages/spec/personal/rules/ui/page.tsx:75`
页面渲染了"搜标题/搜标题和内容"的筛选，但整条链路（SWR key、`listRulesDtoSchema`、后端查询）都没消费它，后端固定两列都搜。更糟的是切换筛选会把 `?filter=` 写进 URL，而路由层用 strictObject 的 `listRulesDtoSchema.parse` 只摘了 `view`，未知键 `filter` 在开发环境直接抛 ZodError 崩到错误页。
**修法**：要么把 filter 真正接入 DTO → 查询链路，要么先撤掉 filters/defaultFilter 退化为纯搜索框；路由层解析前应剥离所有非 DTO 参数或改 safeParse 回退。

**9. 规约列表未消费分页：超过 30 条被静默截断** — `src/pages/spec/personal/rules/ui/list.tsx:31`
后端返回 `hasMore/nextOffset/total`，前端只 `useSWR` 拉一次不带 offset，第 31 条起在两种视图都不可见，也无"加载更多"。收录页已有 `useSWRInfinite` + 哨兵 + `InfiniteListFooter` 的完整实现可直接对照。
**修法**：参照收录页改 `useSWRInfinite`；最小修复也应展示 total 并在 hasMore 时给"加载更多"按钮。

**10. 编辑页丢失空间上下文：文件夹下拉列错空间，保存会把规约静默迁到默认空间** — `src/pages/spec/personal/rules/ui/edit-page.tsx:57`
`EditRulePage` 没给 `RuleEditorForm` 传 `spaceId`（创建页传了），`ruleContentVo` 也不返回 spaceId。编辑非默认空间的规约时下拉列出的是默认空间的文件夹；选中保存后端会按目标文件夹把规约整条迁到默认空间，保存后跳转又不带 spaceId，用户会以为规约丢了。另外详情拉取失败会永远停在 loading（`edit-page.tsx:48`）。
**修法**：`ruleContentVo` 返回 spaceId 并透传给表单/下拉；保存后跳转带回 `?spaceId=`；补错误态。

### D. 前端功能缺陷（4 项）

**11. 「使用此版本」竞态会清空收录的文件夹和标签** — `src/pages/spec/personal/prompt/records/ui/edit-record-dialog.tsx:92`
有 `useVersionId` 时 loading 门槛只等 versionContent 不等 fullRecord，此时弹窗已可交互；fullRecord 未返回前关闭弹窗会触发"关闭即保存"，不变检查因 fullRecord 为 undefined 被跳过，最终以 `folderId: null, tags: []` 更新——收录被移出文件夹、标签全清。版本详情请求失败还会无限 loading。
**修法**：loading 条件改为 `isLoading || !fullRecord || (useVersionId ? !versionContent : false)`；给版本详情失败提供关闭/重试出路。

**12. 编辑器偏好的 zod `.default()` 被误当"parse 失败回退"，脏数据会静默丢弃整份偏好** — `src/features/markdown-editor/lib/editor-prefs-schema.ts:19`
注释宣称"parse 永不抛错、非法值回退默认"，但 `.default()` 只在 undefined 时生效：任意一个字段非法（如旧版本残留主题 id）都会抛 ZodError，被 zustand persist 的 hydrate 静默吞掉，结果整份持久化偏好（主题+设置+快捷栏）被丢弃回默认，与设计意图完全相反。三个 `safeParseXxx` 导出全仓无人使用且内部仍是会抛的 `.parse`。
**修法**：改用 zod 的 `.catch(默认值)`，或 merge 时逐字段 safeParse 只回退非法字段；删除死导出、修正注释。

**13. auth 布局用持久化 setTheme 强制暗色，OAuth 跳转后永久覆盖用户主题** — `app/spec/(auth)/layout.tsx:13`
`setTheme("dark")` 写 localStorage，卸载时恢复的是硬编码 `"system"`（覆盖用户显式选的 light/dark）；而 GitHub/Google 登录是全页跳转，cleanup 根本不执行，localStorage 里的 dark 被永久保留——每次 OAuth 登录后主题都被静默改暗。
**修法**：改为在 auth 布局容器上挂 `dark` class（Tailwind dark 变体按子树生效，零副作用）；该逻辑同时应下沉到 `src/app/layouts` 保持路由层薄。

**14. 登录/注册页的服务条款与隐私政策链接指向无关产品 dub.co** — `src/widgets/auth-form-layout/ui/layout.tsx:23`
从 Dub 开源代码抄袭的残留：所有鉴权页底部的"服务条款""隐私政策"会把用户带到另一家公司的法律页面。`showTerms` 的恒真判断也是死条件。同源残留还有邮件 `replyTo: support@dub.co`（`src/server/infrastructure/email/resend/send.ts:36`）。
**修法**：链接与 replyTo 收敛到自己的 appConfig；顺手清掉恒真判断。

### E. 样式失效与死代码（2 项）

**15. content-card 的 inset-shadow 写法非法，整卡 box-shadow（含外层投影）完全失效** — `src/shared/ui/content-card.tsx:105`
两个同名 `inset-shadow-[...]` 任意值类互相覆盖（只有一个生效），且胜出值里的 `white/30` 不是合法 CSS 颜色，代入 `var(--tw-inset-shadow)` 链后整条 box-shadow 在 computed-value 阶段失效——第 104 行精心设计的双层投影和 hover 加深实际一个都没渲染（已用项目内 tailwindcss 4.2.4 编译验证）。
**修法**：两道 inset 合并进一个 utility 并用合法颜色：`inset-shadow-[1px_1px_0_rgba(255,255,255,0.3),-1px_-1px_0_rgba(0,0,0,0.06)]`（dark 同理）；顺带把硬编码 oklch 灰换主题 token。

**16. sidebar.tsx 779 行整文件死代码，连带 sheet.tsx、sonner.tsx** — `src/shared/ui/sidebar.tsx:1`
`sidebar.tsx` 全仓零引用；`sheet.tsx` 唯一消费者是它，连带死亡；`sonner.tsx` 是 `features/toast` Toaster 的旧版重复实现，也无引用。三个文件约 35KB。
**修法**：直接删除（含仅被它们引用的配置常量）；将来需要时 `npx shadcn@latest add` 重新拉即可。

## 二、需要优化的问题（P1，按主题分组）

以下为中等严重度里最值得处理的，完整清单见附录。

### 后端正确性与安全加固

- **复制计数端点**：where 缺 ownerId 可刷他人热度；`updateMany` 会触发 `@updatedAt`，本人复制一次就把收录顶到"最近更新"首位（`app/api/prompt/records/[id]/copies/route.ts:14`）。
- **版本号竞态**：取 max+1 无 `(recordId, versionNumber)` 唯一约束兜底（`app/api/prompt/records/[id]/route.ts:106`）；仅改名也会产生空 diff 版本（同文件 :94）。
- **OTP 用 `Math.random()` 生成**，非密码学安全随机（`src/shared/lib/auth/utils.ts:6`）。
- **限流 key 里 `getIP()` 未 await**，插值成 `[object Promise]`，邮箱+IP 双维度限流退化（`src/server/actions/auth/send-otp.ts:41`）；429 永远带不上 Retry-After（`with-session.ts:43`）。
- **头像 data URL 无大小上限**，可提交超大 body（`app/api/user/route.ts:34`）。
- **规约挂文件夹未校验 resourceType**，可把规约挂到提示词文件夹（`app/api/rules/route.ts:125`）；folders/tags 的 GET 裸解构 searchParams 未过 Dto（`app/api/folders/route.ts:19`）。
- **邮箱变更的取消/确认写操作放在 pages 层服务端组件渲染中**，取消分支无鉴权，可被链接扫描器 GET 误触发（`src/pages/spec/auth/confirm-email-change/ui/confirm-flow.tsx:33`）。
- **全站无安全响应头**（X-Frame-Options / CSP / HSTS，`next.config.ts`）。

### 前端功能缺陷

- 三个创建对话框（folder/tag/space）**无提交中状态**，双击会重复创建（`src/features/folder-combobox/ui/create-folder-dialog.tsx:52`）。
- 复用草稿**部分失败处理颠倒**：收录已创建却提示"复用失败"，重试产生重复收录（`promote-draft-dialog.tsx:70`）。
- 规约**保存失败无任何用户反馈**（未处理的 Promise 拒绝，`rule-editor-form.tsx:102`）。
- 两处按钮标着快捷键 **`C` 但全仓没有注册任何按键处理器**（records `page.tsx:158`、rules `page.tsx:63`）。
- `tag-chip` 的 color-mix 用了**不存在的 CSS 关键字 `text`**，整条颜色声明失效（`tag-chip.tsx:36`）；`auth-methods-separator` 引用不存在的 `text-content-muted` token 且硬编码浅灰在暗色下失效。
- 注册页"继续"按钮 `type=submit` 但**组件内没有 form**，点击无效果（`verify-email-form.tsx:119`）；signup-form 分隔线条件会渲染字面量 `0`。
- SWR 全局 onError 同样作用于 useSWRMutation，**mutation 失败弹两条重复 toast**（`delete-rule-dialog.tsx:39`）。
- markdown-editor 的 `isPreview/activeFormats` 等**实例态放在模块级单例 store**，多编辑器实例互相污染（`editor-store.ts:30`）。
- `tagIds` 筛选注释写 AND、实现是 OR，**语义自相矛盾**（`src/shared/lib/zod/schemas/rule.ts:114`）。

## 三、可以简化的代码（重复与冗余）

### 1. combobox 家族"三胞胎"（最大的一块重复）

## 四、代码结构梳理建议（系统性）

### 1. 守住 FSD 的公有 API 边界（当前最普遍的违规）

深层导入绕过 slice `index.ts` 的情况已在多层扩散：pages 跨 slice 导入 prompt 内部文件（`version-list-panel.tsx:5`）、records/drafts 的公有 API 不完整迫使 4 处深层导入（`src/entities/prompt/records/index.ts`）、`filter-combobox` 深层导入 `tag-combobox` 内部、注册页深层导入 `ui/page`，等等（附录 structure 类共 13 处）。

**建议**：① 先补齐各 slice 的 `index.ts` 桶导出，把现有深层导入改回公有 API；② 引入边界 lint 固化规则（如 steiger（FSD 官方 linter）或 biome 的 import 限制），让违规在 CI 报错而不是靠 review 记忆。

### 2. 理清 shared ↔ server 的双向穿透

三个方向的越界互相纠缠：客户端组件直接 import `src/server` 运行时代码（`keys-table.tsx:9`，服务端 RBAC 被打进客户端 bundle）；`src/server/rbac/resource-ui.ts` 混入纯前端 UI 元数据；`src/shared/lib/zod` 反向依赖 src/server 常量；`src/shared/ui/file-upload.tsx` 又反向依赖 features 层的 toast。

**建议**：把"前后端都要用的纯数据"（scope 定义、资源元数据、常量）收敛到 `src/shared` 下的一个纯数据模块（无运行时副作用），server 与前端都从它导入；shared/ui 组件通过 props 回调上抛错误而不是直接依赖 features/toast。

### 3. 把放错层的模块归位

- `command-scroll-mask`：无业务语义的通用 UI，从 features 降到 `src/shared/ui`。
- `InfiniteListFooter`：已被无关 slice 跨层引用，上移到 `src/shared/ui`。
- 通用 `VersionPage`：被 records/versions 同层导入，下沉为 widget。
- 邮箱变更的确认/取消写逻辑：从 pages 的 ui segment 移到 `app/api`（或 server action），顺带解决其无鉴权 GET 触发问题。

### 4. 用"基座 + 配置"消灭三对双胞胎

上文"可简化"部分的三大块重复（combobox 家族、records/drafts、error 页/OAuth 按钮）本质是同一个问题：**新功能靠复制旧功能起步，改造只落在其中一份上**。规约库改造后建议安排一次专门的"合并双胞胎"迭代，优先级：combobox 基座 > drafts 同步单例编辑器 > 后端列表查询 helper > error/OAuth 收敛。规约列表的分页也应直接复用收录页的 `useSWRInfinite` 方案，而不是再长出第三种列表实现。

### 5. 鉴权防线的三层统一

当前三层各有缺口且策略分散：页面层（proxy.ts 空守卫）、路由层（permissions 可选导致漏配）、错误层（HTTP API 不脱敏）。建议一次性定型：

1. `proxy.ts` 做统一登录守卫（P0 第 1 条）；
2. `withPersonal` 的 `permissions` 参数**改为必传**（不需要 scope 的路由显式传空数组表意），从类型上杜绝"忘了传就等于不校验"；
3. 错误响应统一走脱敏出口（P0 第 4 条），Server Action 与 HTTP API 共用一套策略。

### 6. 工程基建补课

- **测试**：vitest 已在 package.json 接线，先补配置文件 + 对本次 P0 修复各写一条回归测试（通配 scope、默认空间幂等、编辑器偏好回退），把"修 bug 必附测试"立为惯例。
- **env 管理**：建一个集中的 env 校验模块（zod 解析 process.env，启动即报缺失），同步补齐 `.env.example`；Axiom 惰性初始化后崩溃问题也随之解决。
- **demo 路由**：`app/demo`、`src/pages/demo` 加生产守卫或移出 app 路由树。
- **文档同步**：更新 `src/shared/lib/AGENTS.md`（已整体过时）；`docs/` 下"变动/待处理/测试/设计-demo"等目录建议加一个索引 README 说明各自用途，避免混放。

### 7. 命名与规范小项

新文件 `src/app/providers/KBar.tsx`、`Interactive-grid-pattern.tsx` 违反根规范强制的 kebab-case；删除弹窗文案"规则"与全站统一的"规约"术语冲突；token-actions 直接从 lucide-react 导入图标绕过 icons.tsx 注册表。这类问题建议在合并双胞胎迭代时顺手清理。
